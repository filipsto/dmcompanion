# Entities Report Workflow

Run **Generate Entities Report** on a design's **Logical** tree node. The report includes entities only, not entity views or relationship articles. Its setup dialog follows the Tables Report: choose a Reports folder, title, filename, HTML or PDF (when `dmc.reports.edgeExecutablePath` is set), sections, entities, and logical diagrams. Existing filenames are never overwritten. HTML uses the versioned `tables-report.*.css` stylesheet and optional `tables-report.custom.css` in the Reports folder; PDF uses the bundled stylesheet and a temporary Edge staging directory.

If `dmc.sddmSystemDataTypesPath` is configured, **Templates** offers applicable entity sections from `report_templates.xml`, and **Objects** offers applicable entity/diagram selections from `standard_reports_configurations.xml`. Both are filtered by SDDM design ID and logical model ID. The logical ID is retained when importing a design. Older DMC imports can read it from the original SDDM `logical/Logical.xml` when that source still exists; without an ID, model-scoped presets are not offered. Choices from presets remain editable.

Entity articles begin with name, preferred abbreviation, classification, supertype, and synonyms. Sections then appear in this order: Description and Notes, Mapped Tables (resolved by relational model ID and table ID), Attributes, Attributes Comments, Identifiers, Constraints, Relationships, Relationship Attributes, Dynamic Properties, and Used In Diagrams. Empty and disabled sections are omitted. Model names are disambiguated with their IDs only when names collide.

Relationships are listed for both participating entities, with links in **Other Entity** only when those articles are included. **Role** is the label at the described entity's endpoint; **Other Role** is the opposite endpoint's label. **Cardinality** combines optionality and cardinality: optional ends use `0:1` or `0:*`, and mandatory ends use `1:1` or `1:*`. There is no separate Optionality column. **Identifying** shows `Yes` only for identifying relationships; otherwise it is blank. **Non Transferable** is blank unless at least one endpoint's `sourceTransferable` or `targetTransferable` flag is explicitly `false`. When either end is non-transferable, both endpoint values are shown: `Yes / No`, `No / Yes`, or `Yes / Yes`. A missing or `true` transferability flag means that endpoint is transferable (`No` in Non Transferable).

Cardinality and Non Transferable show the described entity's value first and the other entity's value second, separated by ` / `, without Source/Target prefixes. Self-references appear once, with target-side roles and values first, then source-side roles and values. Missing labels and cardinalities remain blank; when cardinality is known but optionality is missing, the stored cardinality is shown without a lower bound.

When relationships have attributes, **Relationship Attributes** follows Relationships with columns Relationship, Attribute Name, M, Data Type, Domain, and Formula (Default Value). The relationship name appears only on its first attribute row, with blank Relationship cells on subsequent rows; each new relationship starts with its name. Relationships follow the same sorting as the Relationships table and attributes retain their stored order. Mandatory attributes show `Y` in M. Type/domain resolution and formula/default formatting match entity attributes. The existing **Relationships** checkbox in Templates controls both relationship tables, independently of the entity Attributes checkbox.

The SDDM `entity_constraints` template flag controls Constraints, which contains only attribute and domain checks. The Constraints table shows Domain Comment for existing check rows when the attribute uses a domain as its data type; it does not show check Comment or Notes. Attributes show **Keys** as `P` or `U`, with `F` appended only for an explicit logical relation-attribute ID match. Separate PK/FK and DT kind columns are not shown. Identifiers include Comment and Notes rather than Element Type or relationship labels. Entity dynamic properties matched to entity UDP definitions in the configured SDDM system data types directory are marked **UDP** and link to a deduplicated **Used User defined properties** section before Diagrams; that section also appears in the table of contents. Unmatched dynamic properties remain unmarked.

Selected diagrams render through the normal model-linked logical diagram workspace. Entity articles link to their placements, and selected entity card headers link back to report articles. The renderer uses the full logical model so filtering report articles does not remove other cards from the diagram. Failed diagram tabs show an error section while the other content is still generated.

An embedded Diagram View links to another diagram only when that target is included in the report. Imported SDDM notes may have no saved font size: SDDM can reset a note's custom font size when its design is reopened. DMC logical diagrams use the rendered default for such notes and persist font-size changes made in the VS Code note editor independently of the SDDM source.
